# DECISIONS.md

Registro de decisões tomadas de forma autônoma diante de ambiguidades do PRD, conforme a regra 3 do prompt de contexto. Cada entrada tem uma linha de justificativa.

## Remoção de chave de API pela UI (2026-08-25)

- **Hard delete, não soft-delete**: `deleteApiKey` (`apps/web/src/lib/api-keys.ts`) apaga a linha da tabela `api_keys` de vez (`prisma.apiKey.deleteMany`), em vez de marcar um campo tipo `ativa: false`. Motivo: (1) nada no app precisa de histórico/auditoria de chaves removidas (diferente de `Article`, cujo histórico é requisito explícito do PRD); (2) a constraint única `@@unique([userId, provider, tipo])` já existe e o fluxo de recadastro usa `upsert` — soft-delete exigiria excluir linhas "removidas" dessa constraint e de toda leitura (`listApiKeyCards`, `getDecryptedApiKey`, `listConfiguredProviders`) para não bloquear/confundir um recadastro, complexidade sem benefício real num app pessoal de usuário único.
- **`deleteMany` em vez de `delete`, de propósito**: `delete` lançaria `RecordNotFoundError` se a chave já não existisse; `deleteMany` apaga zero linhas silenciosamente. Isso torna a operação idempotente (RF implícito: clicar "Remover" duas vezes, ou a chave já ter sido removida em outra aba, nunca deveria virar erro 500) sem precisar de um `findFirst` prévio.
- **Chave compartilhada (OpenAI/Gemini/OpenRouter) reflete nos dois cards automaticamente, sem código extra**: como `tipoForSave` já mapeia esses provedores para uma única linha `tipo=AMBOS`, e `listApiKeyCards` já lê essa mesma linha para os dois cards (texto e imagem) via `tiposToQuery`, apagar essa linha uma vez já é suficiente — não existe uma "remoção em cascata" para implementar, é a mesma leitura que já existia refletindo o novo estado.
- **Rota `DELETE /api/api-keys/[provider]/[capability]`** (dynamic route params, não query string): segue o mesmo padrão já usado em `/api/wp-sites/[id]` e `/api/production-lines/[id]/titles/[titleId]`, em vez de introduzir um estilo novo de rota com query string só para esse endpoint.
- **Sem endpoint dedicado de "remoção em lote"**: cada card dispara sua própria chamada DELETE; como a operação já é idempotente e barata, não há necessidade de um endpoint que remova várias chaves de uma vez.

## OpenRouter como provedor de imagem (2026-08-25)

- **Motivo de negócio**: evitar depender só da cota diária gratuita do Gemini direto (1500 req/dia texto, **500/dia imagem**, já esgotada em testes anteriores — ver PROMPT 2/3) e consolidar o billing pago em um único provedor (OpenRouter), já integrado para texto nesta mesma entrega.
- **Endpoint próprio, diferente do de texto**: o OpenRouter tem uma Image API dedicada (`POST /images`, formato de request/response distinto de `/chat/completions`) — `createOpenRouterImageProvider` (`packages/shared/src/ai/openrouter.ts`) implementa `ImageProvider` chamando esse endpoint, reaproveitando a mesma constante `EXTRA_HEADERS`/autenticação Bearer do provider de texto no mesmo arquivo.
- **Modelo padrão confirmado na fonte (2026-08-25)**: `google/gemini-2.5-flash-image` ("Nano Banana") via `GET /api/v1/models?output_modalities=image` — mesmo modelo comercial já usado no provider Gemini direto, agora acessível também via OpenRouter. Configurável por `OPENROUTER_IMAGE_DEFAULT_MODEL`.
- **Imagens de referência via `input_references`** (array de `{ type: "image_url", image_url: { url } }`, aceitando `data:` URL): o array de `referenceImages` (já limitado a 5 por linha em `production-lines.ts`, RF-25) é repassado integralmente como `data:${mimeType};base64,${base64}` — nenhum limite adicional no provider, mesmo padrão do `gemini.ts` (que também apenas itera o array recebido).
- **Fallback silencioso quando o modelo não suporta `input_references`**: a API não tem um jeito barato de checar `supported_parameters` do endpoint antes de cada chamada (exigiria uma requisição extra à Image Models API a cada geração), então o cliente tenta com referência e, se o OpenRouter responder 400 mencionando `input_references` no corpo, refaz a chamada sem referência (loga um aviso, não falha o artigo). Um 400 por outro motivo (ex.: prompt ausente) continua propagando o erro normalmente — só esse padrão específico aciona o fallback.
- **Reaproveita o `AiErrorCode` "insufficient_credits"** já criado para o provider de texto (mesmo status 402, mesma API/conta de billing do OpenRouter).
- **Chave compartilhada entre texto e imagem (RF-13)**: `tipoForSave` (`apps/web/src/lib/api-keys.ts`) passou a tratar `OPENROUTER` como `AMBOS`, igual a OpenAI/Gemini — o card na aba "IAs para Imagens" reaproveita a mesma chave já validada na aba de texto, sem pedir de novo (mesmo mecanismo de `listApiKeyCards`/`ProviderCard`, nenhuma tela nova).
- **Sem select hardcoded para ajustar**: adicionar a entrada em `IMAGE_PROVIDERS` (`packages/shared/src/ai/registry.ts`, com `suportaImagensReferencia: true`) foi suficiente para o OpenRouter aparecer nos selects de "IA para imagem" de Criar Artigo e Nova Linha de Produção — ambos já liam a lista de provedores configurados dinamicamente (confirmado na entrega do provider de texto).

## OpenRouter como novo provedor de texto (2026-08-25)

- **Motivo de negócio**: OpenRouter foi adicionado como alternativa de pagamento ao DeepSeek direto — a API oficial da DeepSeek exige cartão internacional (bloqueado para o usuário) e/ou tem mínimo de recarga alto para uso pessoal esporádico. O OpenRouter aceita outros métodos de pagamento e permite recargas pequenas, servindo o mesmo modelo (DeepSeek V4 Flash) via uma API compatível com o formato da OpenAI.
- **Reaproveitamento total da abstração `TextProvider`**: `createOpenRouterTextProvider` (`packages/shared/src/ai/openrouter.ts`) é estruturalmente idêntico ao `createOpenAiTextProvider`/`createGrokTextProvider` (mesmo padrão de `chatCompletion` via `/chat/completions`) — só mudam `base_url`, o nome do modelo e dois headers extras (`HTTP-Referer`/`X-Title`, recomendados pelo OpenRouter para identificar a aplicação, valores genéricos do projeto). Mantido o mesmo grau de duplicação entre arquivos de provedor que já existia entre `openai.ts`/`grok.ts` (nenhuma fábrica genérica foi extraída), por consistência com o padrão já estabelecido no código.
- **Só texto por enquanto**: o catálogo de imagem do OpenRouter não segue o mesmo formato request/response simples de texto — fora de escopo desta entrega. `createImageProvider`/`createTextProvider` lançam erro explícito se chamados com a combinação provedor/capacidade errada (mesmo padrão já usado para a Stability, que só faz imagem).
- **Slug do modelo confirmado na fonte (2026-08-25)**: `deepseek/deepseek-v4-flash-0731` é o build oficial do DeepSeek V4 Flash re-treinado, publicado em 31/07/2026 no catálogo do OpenRouter — `deepseek/deepseek-v4-flash` (sem sufixo) é o preview antigo de abril/2026 e foi evitado. Configurável via `OPENROUTER_DEFAULT_MODEL` (nome pedido explicitamente, diverge da convenção `_TEXT_MODEL` dos demais provedores porque o OpenRouter só tem modelo de texto nesta versão).
- **Novo `AiErrorCode` "insufficient_credits"** para o HTTP 402 (saldo/créditos esgotados no OpenRouter, confirmado na documentação oficial `openrouter.ai/docs/api_reference/limits`) — distinto de `rate_limit` (429) porque a ação do usuário é diferente (recarregar saldo vs. esperar/trocar de provedor) e o PRD pediu uma mensagem específica em português. Adicionado de forma genérica em `classifyHttpError` (por status HTTP, não por provedor), já que nenhum outro provedor hoje usa 402 — se algum passar a usar, ganha a mensagem certa de graça.
- **Card em "Chaves de API" e selects de "IA para texto" sem nenhuma tela nova**: `ApiKeysClient`/`ProviderCard`, a página de Criar Artigo e o modal de Nova Linha de Produção já liam `TEXT_PROVIDERS`/`listConfiguredProviders` dinamicamente (nenhum select hardcoded existia) — adicionar o OpenRouter em `TEXT_PROVIDERS` (`packages/shared/src/ai/registry.ts`) foi suficiente para aparecer em todos os lugares certos.
- **Validação da chave via `GET /api/v1/models`**: endpoint gratuito do OpenRouter (não consome créditos), mesmo padrão já usado para validar a chave da OpenAI/Grok.

## Deploy do "web" na Railway — remoção do `output: "standalone"` (2026-08-25)

- **Bug real em produção**: o serviço "web" na Railway (build via Railpack, sem Dockerfile customizado) falhava logo após o start com `"next start" does not work with "output: standalone" configuration` e o processo caía por `SIGTERM` em loop. Causa: `next.config.mjs` desativava `standalone` só quando `process.env.VERCEL` estava definido (ver decisão anterior), mas a Railway não define essa variável — então o build gerava `.next/standalone`, e o script `"start": "next start"` do `apps/web/package.json` (inalterado, é o padrão do create-next-app) é incompatível com esse modo, que exigiria `node .next/standalone/server.js`.
- **Corrigido removendo `output: "standalone"` por completo** do `next.config.mjs`, em vez de estender a condicional para também detectar a Railway (ex.: `RAILWAY_ENVIRONMENT_NAME`). Motivo: nem Vercel nem Railway (os dois destinos reais do "web" hoje) fazem build a partir de `apps/web/Dockerfile` ou leem `.next/standalone` — ambos usam Railpack/empacotamento nativo próprio. Manter `standalone` como caso especial só complicava o `package.json` (exigiria trocar `start` condicionalmente por plataforma) sem nenhum benefício.
- **Efeito colateral aceito conscientemente**: `apps/web/Dockerfile` (usado pelo caminho alternativo "VPS único" via `docker-compose.prod.yml`, descrito no `README.md` e validado no PROMPT 4) depende de `.next/standalone` e **para de funcionar** para o `web` a partir desta mudança — decisão confirmada com o usuário, que optou por abandonar esse caminho para o `web` em favor de Vercel/Railway. O Dockerfile foi marcado como obsoleto (comentário no próprio arquivo) em vez de removido, para não destruir histórico/documentação sem necessidade. O `apps/worker/Dockerfile` **não** é afetado — é um build separado, multi-stage com `node` puro, que nunca dependeu do output do Next.js.

## Deploy na Vercel — correção do build do monorepo

- **Bug real encontrado no primeiro deploy na Vercel**: `Module not found: Can't resolve '@wordbee/db'`. Causa: a Vercel roda o build com "Root Directory" = `apps/web` (suporte nativo dela a monorepos — instala a partir da raiz do workspace, mas builda a partir do subdiretório), então `npm run build` executava só o script do `apps/web/package.json` (`next build`), pulando o script raiz `build:libs` que compila `packages/shared` e `packages/db` para `dist/` antes. Localmente isso nunca apareceu porque sempre rodamos o build a partir da raiz do monorepo.
  - **Corrigido tornando `apps/web/package.json`'s `build` autossuficiente**: `"build": "cd ../.. && npm run build:libs && cd apps/web && dotenv -e ../../.env -- next build"` — funciona não importa de onde a plataforma de deploy invoque `npm run build` (raiz ou `apps/web`), sem depender de configurar corretamente o "Root Directory"/"Build Command" no painel da Vercel. Testado localmente simulando exatamente o comportamento da Vercel (build direto de dentro de `apps/web`, sem `dist/` pré-existente).
- **`output: "standalone"` desativado automaticamente na Vercel** (`process.env.VERCEL ? undefined : "standalone"`): esse modo é só para o deploy via Docker/VPS, onde `apps/web/Dockerfile` espera `.next/standalone`. A Vercel usa seu próprio empacotamento serverless e não precisa (nem deveria receber) esse output — a Vercel define `VERCEL=1` automaticamente em todo build, então a mesma base de código serve os dois destinos sem arquivo de config separado.

## PROMPT 4 — Fidelidade visual, robustez e deploy

- **SSRF completo com resolução de DNS** (`assertSafeWordPressUrl` em `packages/shared/src/wordpress/url-guard.ts`): além do bloqueio de IP/hostname literal (PROMPT 2), agora resolve o hostname via `dns.promises.lookup` e bloqueia se qualquer endereço resolvido cair em faixa privada — impede que um domínio público aponte (ou seja re-apontado depois, DNS rebinding) para a rede interna. Não elimina 100% o TOCTOU entre a checagem e a conexão (exigiria fixar o IP resolvido no socket do fetch), mas cobre o caso prático relevante para um app pessoal. 5 novos testes.
- **Indicador de saúde do worker via heartbeat no Redis** (`packages/shared/src/worker-health.ts`), não uma tabela no Postgres: o worker grava `worker:heartbeat` a cada 30s com TTL de 90s (a chave expira sozinha se o worker cair, sem precisar de lógica extra de "está vivo?") e `worker:last_success` a cada publicação bem-sucedida. O Dashboard lê os dois via o mesmo Redis já usado para rate limit de login.
- **Logs do worker em JSON estruturado** (linha, evento, detalhe, duração do "tick") em vez de texto livre — mais fácil de agregar/filtrar em produção (`docker compose logs worker | jq`).
- **Toasts adicionados nos fluxos que só tinham feedback inline** (Chaves de API, cadastro/edição de site, criação de linha, resultado do gerador de artigo) para atender "toasts para toda ação de sucesso/erro" — mantendo também o feedback inline onde ele já fazia sentido (erros de validação de formulário).
- **`loading.tsx`/`error.tsx` no nível do grupo `(dashboard)`**, não por página: como todas as páginas do painel compartilham o mesmo layout e a mesma necessidade de skeleton/estado de erro, um par de arquivos no grupo já cobre a árvore inteira (convenção do App Router) sem duplicar 7 vezes.
- **Backup/restore via `pg_dump`/`pg_restore` em scripts shell simples** (`scripts/backup.sh`/`restore.sh`) em vez de uma ferramenta dedicada — suficiente para um Postgres único de uso pessoal, sem dependência nova. `restore.sh` exige confirmação digitada (`restaurar`) por ser destrutivo.
- **Dockerfiles multi-stage buildados e testados de verdade** (não só escritos): usei `colima` para ter um daemon Docker neste ambiente, buildei as duas imagens, subi a stack completa via `docker-compose.prod.yml` (Postgres+Redis+web+worker), rodei migração e seed exatamente como documentado no README, e confirmei login funcionando através do container na porta 3000. A imagem do worker copia `node_modules` completo (não passa pelo tracing do Next), já que ele roda via `node` puro e precisa do `prisma` CLI disponível para `migrate deploy`/seed em produção.
- **Sem CSRF token dedicado**: os cookies de sessão usam `SameSite=Lax` (já configurado no PROMPT 1), que por padrão do navegador não é enviado em requisições cross-site que não sejam navegação de topo — cobre o cenário relevante de CSRF para as rotas de mutação da API sem precisar de um token extra, aceitável para um app single-user sem endpoints de mutação públicos além do login.

## PROMPT 3 — Linhas de Produção, worker, fila de títulos e histórico

- **Agendamento via job BullMQ auto-reagendado (jobId = lineId) em vez de repeatable jobs nativos do BullMQ.** Repeatable jobs do BullMQ são difíceis de reconfigurar dinamicamente (pausar/retomar/mudar intervalo por linha). Em vez disso, cada execução ("tick") agenda explicitamente a próxima via `scheduleLineRun(lineId, delayMs)` — com `jobId=lineId` garantindo no máximo uma execução pendente por linha. O reagendamento acontece só depois que o job atual termina (dentro do próprio processor, não em um listener "completed"), evitando qualquer condição de corrida no reuso do jobId.
- **"Um tick da linha nunca lança para o BullMQ."** `runProductionLine` captura e trata todo erro internamente (grava `Article` como FALHA, atualiza contadores, reagenda) e sempre retorna normalmente. Toda a lógica de retry (3 tentativas com backoff) e as regras de negócio (máximo atingido, rate limit, 5 falhas consecutivas) vivem dentro dessa função — o BullMQ nunca precisa saber de nenhuma dessas regras nem fazer retry de job.
- **Lock por linha via Redis `SET NX PX`** (chave `line-lock:{lineId}`, TTL de 10 min), adquirido pelo processor do BullMQ antes de chamar `runProductionLine` e liberado no `finally`. Garante que, mesmo que dois processos worker rodem por engano ao mesmo tempo (ex.: deploy com múltiplas réplicas sem querer), a mesma linha nunca é processada em paralelo.
- **Concorrência por provedor de IA via semáforo Redis (`INCR`/`DECR` com poll curto)**, não um limitador nativo do BullMQ (que limitaria por fila inteira, não por provedor). `AI_PROVIDER_CONCURRENCY` (padrão 3) limita quantas chamadas simultâneas por provedor rodam entre todas as linhas ativas.
- **Idempotência via `idempotencyKey` determinística**: `line:{lineId}:title:{titleQueueItemId}` quando o título vem da fila, ou `line:{lineId}:adhoc:{timestamp}` quando é gerado na hora. Antes de processar, o worker verifica se já existe um `Article` não-FALHA com essa chave e, se existir, pula (idempotência real contra reprocessamento).
- **Retry parcial e inteligente**: cada nova tentativa dentro do loop de 3 releem o `Article` do banco e só regeram o que ainda falta (conteúdo/imagem já persistidos numa tentativa anterior não são regerados). Isso exigiu adicionar `wp_media_id`, `ia_texto`, `ia_imagem`, `categoria_wp_id`, `wp_status_alvo`, `tema` e `prompt_customizado` ao modelo `Article` (4 migrações pequenas) — sem esses campos não seria possível reenviar ou retomar um artigo sem regerar tudo à toa, requisito explícito do PRD.
- **Rate limit vs. sobrecarga temporária tratados igual no nível da linha**: tanto `rate_limit` (429, cota do usuário) quanto `unavailable` (502/503/504, sobrecarga do provedor) dão positive para "adiar ou pausar" a linha (`rateLimitBehavior`), já que do ponto de vista da automação a ação certa é a mesma. Timeout (nosso próprio limite de 30s) continua contando como falha determinística normal, pois não necessariamente indica problema do lado do provedor.
- **Reposição da fila de títulos**: depois de cada publicação bem-sucedida, o worker gera 1 novo título só se a fila tiver menos de 3 pendentes — evita gerar títulos demais sem necessidade e mantém sempre alguns prontos.
- **"Atualizar" na página de detalhe da linha busca dados via API**, não `router.refresh()` puro, porque a página tem estado local (fila de títulos, galeria de imagens) que precisa ser resincronizado explicitamente após ações do usuário.
- **Histórico com filtros via query string da URL** (Server Component lendo `searchParams`), não uma API de listagem separada — padrão idiomático do App Router, dá paginação/filtro compartilháveis por link de graça.
- **Storage local exige caminho absoluto em `STORAGE_LOCAL_PATH`.** Como `apps/web` e `apps/worker` rodam com `cwd` diferentes (cada um na sua pasta), um caminho relativo resolveria para diretórios diferentes em cada processo — o worker precisa ler as mesmas imagens de referência que o web salvou.
- **`bullmq` adicionado a `serverComponentsExternalPackages` no `next.config.mjs`** (junto com `@node-rs/argon2`): evita que o webpack tente resolver o adaptador opcional `@valkey/valkey-glide` do bullmq (não instalado, não usado — só suportamos Redis puro via `ioredis`).
- **Validação real ponta a ponta do worker (2026-08-24)**: criei uma linha de produção de verdade usando a chave Gemini e o site `rendadinheiro.com.br` já configurados no PROMPT 2. O worker gerou um título real, gerou conteúdo HTML real, e corretamente classificou/tratou tanto um timeout quanto um 429 (mesma cota de imagem gratuita já esgotada do PROMPT 2) — a linha foi reagendada corretamente em ambos os casos, sem travar nem duplicar. Isso revelou e corrigiu dois bugs reais: (1) `handleDeterministicFailure` gravava `nextRunAt` como "agora" no banco enquanto o job real era agendado para `intervaloMin` no futuro — painel mostraria hora errada; (2) faltava log de observabilidade quando o rate limit acontecia durante geração de conteúdo/imagem (só existia para o título). Publicação de fato (upload de mídia + criação do post) segue não validada por falta de cota de imagem disponível — mecanismo já coberto por testes unitários do cliente WordPress (PROMPT 2).

## PROMPT 2 — Chaves de API, Sites WordPress e geração unitária

- **Bug crítico encontrado e corrigido: `fetch` global do Next.js quebra chamadas HTTP server-to-server.** O Next.js substitui `globalThis.fetch` do processo por uma versão própria (camada de cache/instrumentação de dados). Nos testes manuais, essa versão fazia com que respostas de erro HTTP normais (ex.: 401 da OpenAI, 400 da Gemini) virassem exceções genéricas em vez de um `Response` inspecionável, quebrando toda a classificação de erros (RF-15/RF-23). Corrigido importando `fetch` explicitamente do pacote `undici` em vez de usar o global, tanto no cliente de IA (`packages/shared/src/ai/http.ts`) quanto no cliente WordPress (`packages/shared/src/wordpress/client.ts`). Coberto por testes que mockam o módulo `undici` diretamente.
- **Gemini retorna HTTP 400 (não 401) para chave de API inválida.** `classifyHttpError` foi estendido para reconhecer o padrão "API key not valid"/`API_KEY_INVALID` no corpo de respostas 400 e tratá-las como `invalid_key`, além dos códigos 401/403 usados pelos outros provedores.
- **Modelos e endpoints de IA (pesquisados na documentação oficial de cada provedor em 2026-08-24, ver `packages/shared/src/ai/models.ts`):**
  - OpenAI: `POST /v1/chat/completions` (texto, `gpt-4o`) e `POST /v1/images/generations` (imagem, `dall-e-3`), padrão bem estabelecido.
  - Gemini: `POST /v1beta/models/{model}:generateContent` com header `x-goog-api-key`; imagem via `gemini-2.5-flash-image` ("Nano Banana") com `generationConfig.responseModalities: ["TEXT","IMAGE"]` e imagens de referência como `inlineData` nas `parts` do request. **Validado com chave real**: o modelo de texto `gemini-2.5-flash` citado pelo PRD já não existe mais para novas chaves (a própria API retorna 404 recomendando `gemini-3.6-flash`) — o padrão de `GEMINI_TEXT_MODEL` foi atualizado para `gemini-3.6-flash`. O modelo de imagem `gemini-2.5-flash-image` continua válido.
  - xAI/Grok: endpoint de texto compatível com a API da OpenAI (`POST https://api.x.ai/v1/chat/completions`); endpoint de imagem separado (`POST https://api.x.ai/v1/images/generations`). O rótulo comercial "Grok Imagine" (usado na UI, conforme o PRD) mapeia para o model id atual `grok-2-image` na API — configurável via `GROK_IMAGE_MODEL`, documentado por já ter havido troca de nomenclatura no passado.
  - Stability AI: `POST /v2beta/stable-image/generate/sd3` (multipart/form-data), modelo `sd3.5-large`, `Accept: application/json` para receber a imagem em base64 direto na resposta.
- **`metaTitle` retornado pela IA é reaproveitado como título final do post** (quando ≤ 60 caracteres), em vez de descartado. Como o WordPress puro não tem campo nativo de "meta title" sem um plugin de SEO (Yoast/RankMath — fora de escopo do MVP), usar esse título refinado como o próprio `title` do post é a forma mais direta de cumprir o requisito de "SEO básico (meta title ≤ 60 chars)" do PRD sem integrar um plugin.
- **Chave de API só é salva se a validação no provedor for bem-sucedida** (RF-15). Uma chave inválida nunca é persistida — o usuário recebe o erro e pode tentar de novo. Evita que uma chave quebrada fique "configurada" silenciosamente.
- **Progresso em tempo real do gerador unitário via streaming NDJSON** (newline-delimited JSON) em vez de Server-Sent Events. Motivo: o formulário envia a requisição via `POST` com corpo JSON — `EventSource` nativo só suporta `GET`. Um `ReadableStream` simples lido via `fetch().body.getReader()` no cliente evita a complexidade de SSE sem perder o requisito de "progresso visível (título → conteúdo → imagem → publicando)".
- **Guarda anti-SSRF básica (bloqueio de hostname/IP literal privado)** já implementada em `packages/shared/src/wordpress/url-guard.ts` e coberta por testes. A blindagem completa contra DNS rebinding (resolução de DNS antes de conectar) é a varredura de segurança explícita do PROMPT 4 — aqui cobre o caso comum (localhost, 127.0.0.1, RFC 1918) sem bloquear o fluxo de cadastro de site.
- **Tipos client-safe duplicados fora de `@wordbee/shared`** (`apps/web/src/lib/article-type-options.ts`, `criar-artigo-types.ts`, `wp-sites-types.ts`) em vez de importar tipos do barrel `@wordbee/shared` em componentes cliente. O barrel único do pacote (`export * from` em cada módulo) reexporta também os módulos que usam `node:crypto`/`undici`; embora seja teoricamente tree-shakeable, duplicar as poucas constantes/tipos realmente usados no cliente é mais seguro e barato do que arriscar node-builtins vazando para o bundle do browser.
- **Reenvio de imagem de referência (Gemini) não implementado ainda** — RF-21 do gerador unitário não inclui upload de imagens de referência (isso é exclusivo das Linhas de Produção, RF-25, escopo do PROMPT 3). A interface `ImageProvider.generateImage` já aceita `referenceImages` opcional para não precisar mudar a assinatura depois.
- **Novo `AiErrorCode` "unavailable"** adicionado para respostas 502/503/504 (modelo temporariamente sobrecarregado), distinto de `rate_limit` (429, cota do usuário). Descoberto na validação real abaixo — a Gemini retornou 503 "high demand" em `gemini-3.6-flash" durante o teste, e antes disso caía no genérico `unknown`.
- **Validação ponta a ponta com credenciais reais do usuário (2026-08-24)**: chave Gemini real + site WordPress real (`rendadinheiro.com.br`). Resultado: chave validada e salva (compartilhada entre texto/imagem), conexão com o site confirmada como administrador, categorias reais carregadas, título e conteúdo gerados de verdade pela Gemini e o artigo de teste foi salvo como **rascunho** (não publicado) por segurança — quando a etapa de imagem falhou com 429 (cota de geração de imagem da conta Gemini gratuita esgotada, não um bug), o `Article` ficou corretamente com `status=FALHA` e a mensagem de erro certa, visível no Dashboard/Histórico. Prova que o pipeline, a UI de progresso e o tratamento de erro funcionam ponta a ponta contra APIs reais; só não foi possível validar `uploadMedia`/`createPost` de fato por causa da cota de imagem da chave de teste.

## PROMPT 1 — Fundação

- **Gerenciador de pacotes: npm workspaces.** Já disponível no ambiente, zero instalação extra, suporte nativo a monorepo suficiente para o escopo do projeto.
- **ORM: Prisma** (o PRD permitia Prisma ou Drizzle). Prisma tem migrations maduras e o schema da seção 5 do PRD mapeia diretamente para `schema.prisma`.
- **Prisma na major 5 (5.22.x), não a 7.x mais recente.** Evita churn de duas majors no meio da construção; 5.x é estável e bem documentada. Revisitar upgrade pós-MVP.
- **Hash de senha: Argon2** via `@node-rs/argon2` (binário nativo pré-compilado, sem node-gyp). PRD permitia argon2 ou bcrypt; argon2 é a recomendação atual da OWASP.
- **Sessão: JWT assinado (HS256, `jose`) + registro em `sessions` no Postgres**, não NextAuth (proibido pelo PRD) e não JWT puro sem estado. Precisamos revogar sessões individualmente (RF-02 "sessões ativas"), o que um JWT stateless sozinho não permite.
- **Auth em duas camadas.** O middleware (Edge runtime no Next 14, sem acesso a Postgres) faz apenas a checagem rápida de assinatura/expiração do JWT. A checagem autoritativa (sessão revogada?) acontece em `getCurrentSession()` (Node.js runtime), chamada pelo layout do painel e por cada rota de API. Necessário porque o Next 14 não roda middleware em runtime Node.js.
- **Componentes de UI acessíveis via Radix UI** (Dialog, Tabs, Toast, Switch) em vez de implementar do zero. O PRD exige navegação por teclado, ESC para fechar modais e trap de foco — Radix entrega isso pronto e testado.
- **Tema claro/escuro: `next-themes` (localStorage) como fonte da verdade para a UI**, com sincronização best-effort para a coluna `users.tema_ui` a cada troca (fire-and-forget). Evita complexidade de flash-of-wrong-theme no SSR mantendo o campo do schema útil/persistido.
- **Compartilhamento de chave de API (RF-13):** constraint única em `(userId, provider, tipo)`. OpenAI e Gemini salvam com `tipo=AMBOS` (uma linha só, usada nas duas abas). Grok e Stability mantêm linhas separadas por tipo, já que o PRD só cita OpenAI/Gemini como provedores de chave compartilhada.
- **Next.js fixado em `^14.2.35`** (última patch da série 14.2), não Next 15/16. Elimina a maior parte dos CVEs conhecidos sem forçar uma migração disruptiva do App Router no meio da construção. Os achados residuais do `npm audit` (principalmente avisos ligados a Server Actions/RSC cache que não usamos e a um CVE moderado do esbuild que só afeta o dev server) foram aceitos como risco baixo para um app pessoal, single-user, sem CDN na frente, atrás de login — revisitar upgrade para Next 15+ como melhoria futura.
- **`export const dynamic = "force-dynamic"` no layout raiz.** O app inteiro é pessoal e autenticado (saudação por usuário, sessão via cookie) — nada deveria ser pré-renderizado estaticamente. Isso também contorna um bug conhecido do Next.js 14 (`Error: <Html> should not be imported outside of pages/_document` ao gerar `/404`/`/500` estaticamente); ver nota abaixo.
- **Regra dura: nunca definir `NODE_ENV` no `.env`.** Causou o bug acima quando o `dotenv-cli` injetava `NODE_ENV=development` durante `next build` (que precisa rodar como produção). O `next dev`/`build`/`start` e o worker já definem o valor certo sozinhos; documentado em `.env.example`.
- **Resolução dos pacotes internos (`@wordbee/shared`, `@wordbee/db`):** `package.json` expõe tanto `dist/` compilado (usado por produção e por typecheck) quanto o TypeScript fonte via export condition `"development"` (usado por `tsx`/Next em dev). Como nem toda ferramenta ativa essa condition de forma confiável, os scripts `dev`/`dev:worker`/`typecheck`/`build` sempre rodam `build:libs` primeiro para garantir que `dist/` exista.
- **Redis reaproveitado** para BullMQ (worker) e para rate limiting de login (web) — uma única peça de infra a mais, em vez de outra store separada.
- **Dashboard do Prompt 1 é esqueleto estático** (métricas zeradas, sem consulta ao banco). Dados reais são escopo explícito do PROMPT 2 ("DASHBOARD REAL") no documento de prompts.
- **Sem pasta `/referencia` com screenshots do Wordbee** no projeto (mencionada como opcional nas Observações do documento de prompts). A fidelidade visual seguiu a descrição textual do PROMPT 0 (sidebar roxo/grafite, cards brancos raio ~12px, gradiente roxo→magenta, etc.).

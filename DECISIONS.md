## Achado crítico: os dois fixes anteriores de agendamento NUNCA foram commitados nem enviados ao GitHub (2026-08-27, investigação de produção)

- **O que explica "mesmo com o fix aplicado, todo restart reagenda as 5 linhas do zero"**: `git log --oneline -1 -- apps/worker/src/production-line-worker.ts apps/worker/src/line-pipeline.ts packages/shared/src/queue/index.ts` apontou o commit `47d6cb0` (PROMPT 4, muito antes de hoje) como o último a tocar esses arquivos — as duas rodadas de correção feitas nesta mesma conversa (mover reagendamento pra `completed`/`failed`; endurecer `cancelLineRun`/`syncActiveLines` contra job morto) ficaram só no working tree local, nunca viraram commit, nunca foram enviadas (`git push`) e por consequência **nunca puderam ter sido deployadas no EasyPanel**. O worker em produção seguiu rodando o código de antes de qualquer um dos dois fixes o dia inteiro. Isso sozinho explica todos os sintomas relatados — não era necessário nenhum bug adicional para produzi-los.
- **Investigação de produção (só leitura, mesmas credenciais do `.env`) confirma exatamente esse cenário**: `worker:heartbeat` no Redis está fresco (gravado ~30s atrás, TTL cheio) — o **processo está vivo**, não caiu — mas `queue.getJobCounts()` retornou **zero jobs em qualquer estado** (waiting/active/delayed/completed/failed/paused) e as 5 linhas `ATIVA` estão todas com `nextRunAt` no passado e nenhum job na fila (`sem_job`). Isso bate 100% com o bug original (não o "primo"): cada execução tentava reagendar a própria próxima chamada de dentro do processor, colidindo com o próprio `jobId=lineId` ainda `active` — o BullMQ descarta esse `add()` silenciosamente, o job termina, `removeOnComplete` o apaga, e não sobra rastro nenhum. Não foi encontrado nenhum job `failed` preso (o "bug primo" da rodada anterior) — o sintoma observado hoje é 100% explicado pelo bug original sozinho, porque o código que trataria o caso `failed` (handler `worker.on("failed")`) também nunca foi deployado.
- **Linha `cmtau8bzt000313zkolsbcyuj` ("Documentação e Burocracia") investigada especificamente**: chave OpenRouter do usuário existe, é compartilhada (`tipo=AMBOS`) e está com `statusValidacao=true` (validada com sucesso em 2026-08-25) — não é problema de chave. Os 3 artigos que essa linha tentou gerar hoje falharam todos com o mesmo erro das outras linhas ("O OpenRouter demorou demais para responder"), incrementando `consecutiveFailures` para 3 sem nunca completar um ciclo — por isso ela aparece "0/10" mesmo tendo rodado várias vezes: não é um problema adicional dela, é a mesma degradação/timeout do OpenRouter que afeta as outras linhas, só que ela teve azar de nunca completar uma tentativa com sucesso ainda.
- **Decisão**: os dois fixes pendentes (nunca deployados) e a instrumentação desta rodada são enviados juntos nesta sessão — não faz sentido deployar só os logs novos em cima do código antigo e quebrado; a investigação só faz sentido em cima do comportamento corrigido. Ver entrada seguinte para o detalhe da instrumentação.

## Instrumentação para investigar produção sem aplicar mais fixes às cegas (2026-08-27)

- **Contexto**: mesmo topando com o achado crítico acima (que já explica o sintoma principal), a tarefa pedida foi só instrumentar — não presumir que não há mais nada errado (ex.: degradação real do OpenRouter, múltiplas instâncias do worker) só porque a causa óbvia foi encontrada. Toda a instrumentação abaixo continua no código depois que os fixes forem confirmados funcionando, como observabilidade permanente.
- **`workerId` por processo** (`apps/worker/src/production-line-worker.ts`): um `crypto.randomUUID()` gerado uma vez na carga do módulo, logado num evento `worker_instancia_iniciada` (com `pid`) e incluído em TODO log estruturado deste arquivo daí em diante (`tick_concluido`, `lock_ocupado`, `reschedule_pos_completed`, logs de `syncActiveLines`, `heartbeat`). Se dois `workerId` diferentes aparecerem intercalados no mesmo stream de log do EasyPanel, é prova direta de mais de uma instância/réplica rodando ao mesmo tempo — não consigo confirmar isso remotamente sem acesso ao painel do EasyPanel, então essa checagem (item 2 do pedido) fica pendente do lado do usuário; o log deixa a evidência pronta pra quando ele olhar.
- **Log explícito antes/depois de `scheduleLineRun` nos handlers `completed`/`failed`** (`rescheduleIfNeeded` em `production-line-worker.ts`, evento `reschedule_pos_completed` com `fase: "antes"|"depois"`): se "antes" nunca aparecer entre um `tick_concluido` e o próximo restart, o handler não está sendo chamado; se "antes" aparecer sem o "depois" correspondente, `scheduleLineRun` travou ou lançou.
- **`scheduleLineRun` (`packages/shared/src/queue/index.ts`) agora retorna o `Job` criado (era `Promise<void>`) e loga um evento `queue_add`** com o `id`/`delay` **confirmados pelo próprio `Job` retornado pelo BullMQ** (não só os valores pedidos) e o estado do job logo após criar — a fonte de verdade final de que o job realmente existe no Redis, não só que a chamada não lançou. `cancelLineRun` ganhou logs `cancel_line_run_job_encontrado`/`cancel_line_run_job_removido` pelo mesmo motivo, do lado da remoção.
- **Heartbeat de log periódico, distinto do heartbeat de Redis já existente** (`startHeartbeatLog()` em `production-line-worker.ts`, chamado a cada 5 min a partir de `index.ts`, log imediato ao iniciar + a cada intervalo): evento `heartbeat` com `linhasAtivas` (contagem no Postgres) e `jobsNaFila` (`queue.getJobCounts()` completo, todos os estados). O heartbeat de Redis (`recordHeartbeat`, a cada 30s) só alimenta o badge do Dashboard e tem TTL de 90s — não fica visível no stream de log do EasyPanel. Se este heartbeat de log parar de aparecer, o processo morreu/travou sem reiniciar sozinho, e falta configurar restart automático na infra (fora do escopo de código).
- **Latência real do OpenRouter por chamada, mesmo em timeout/erro** (`logOpenRouterCall` em `packages/shared/src/ai/openrouter.ts`, usado por `chatCompletion` — título e artigo, tipos distintos — e `requestImage`): evento `openrouter_call` com `tipo: "titulo"|"artigo"|"imagem"`, `duracaoMs` e `resultado: "ok"|"timeout"|"erro"`. Vai mostrar se toda chamada bate o teto do timeout (60s/90s) — degradação sustentada do provedor — ou se varia (algo mais específico, ex.: só chamadas concorrentes demoram).
- **Nada disso corrige comportamento** — só adiciona `console.log`/`console.error` estruturado e muda o tipo de retorno de `scheduleLineRun` (`void` → `Job`, mudança aditiva, nenhum call site usava o retorno). `typecheck`, `lint`, `build` e os 98 testes automatizados confirmados sem regressão antes do deploy.

## Bug primo do anterior: job "failed" morto podia bloquear cancelLineRun/syncActiveLines pra sempre (2026-08-27, mesmo dia)

- **Investigação em produção (só leitura) não encontrou nenhum job "failed" preso no momento da checagem**: conectei direto no Redis (Upstash) e Postgres (Neon) de produção com as credenciais já presentes no `.env` local e inspecionei as 5 linhas de teste — as 5 estavam com `status=ATIVA`, `nextRunAt` no futuro e um job `delayed` correspondente na fila (`queue.getJobs(["failed"])` retornou 0 em toda a fila). Os 5 jobs tinham timestamp idêntico (~12:22:42–43 UTC do mesmo dia), consistente com terem sido recriados de uma vez por `syncActiveLines()` no boot do worker após o deploy do fix anterior (colisão de jobId) — ou seja, o sintoma relatado ("3 de 5 continuam com `nextRunAt` no passado mesmo após restart") já não estava mais presente no momento desta investigação. Não foi encontrado nenhum stack trace de exceção não tratada nos `Article` com `status=FALHA` recentes — as falhas registradas ali (`"O OpenRouter demorou demais para responder..."`) são timeouts tratados normalmente pelo try/catch de geração, não crashes.
- **A hipótese em si é um bug real, confirmado por revisão de código, não pela investigação ao vivo**: `getDecryptedApiKey`/`getSiteCredentials` e várias outras chamadas ao Postgres em `runProductionLine` (`apps/worker/src/line-pipeline.ts`) rodavam **fora** do try/catch da geração (que só cobre o loop de 3 tentativas de conteúdo/imagem) — uma falha ali (rede, Postgres momentaneamente fora do ar, erro de descriptografia) propagava como exceção não tratada pro processor do BullMQ, e o job virava `failed` de verdade. Combinado com `cancelLineRun()` só removendo jobs `waiting`/`delayed` (não `failed`/`completed`) e `syncActiveLines()` só checando *existência* de job (não o *estado*), uma linha que sofresse UM erro assim ficaria com o `jobId=lineId` ocupado por um job morto pra sempre — nenhum `scheduleLineRun` futuro conseguiria recriar o job, mesmo depois de reiniciar o worker quantas vezes fosse. Esse é o mecanismo exato que teria produzido o sintoma relatado, mesmo sem uma instância viva dele no momento da checagem — o "reagendamento no `completed`/`failed`" implementado no fix anterior no mesmo dia até *tentava* reagendar num crash real, mas ficava neutralizado por essa mesma limitação de `cancelLineRun`.
- **Correção em duas frentes que se reforçam**:
  1. `cancelLineRun()` (`packages/shared/src/queue/index.ts`) agora remove o job existente em **qualquer** estado que não seja `active` (era só `waiting`/`delayed`) — preserva exclusivamente um job realmente em execução agora; `job.remove()` que falhar por corrida (job virou `active` entre o `getState()` e o `remove()`) é tratado com log, não propaga.
  2. `syncActiveLines()` (`apps/worker/src/production-line-worker.ts`) agora checa o **estado** do job existente, não só sua existência — só pula a linha (`continue`) se o estado for `waiting`/`delayed`/`active` (allow-list deliberada); qualquer outro estado é tratado como job morto e a linha é reagendada via `scheduleLineRun` (que agora limpa o job morto de verdade, graças à correção acima).
  3. **Causa raiz do throw não tratado**: `runProductionLine` (exportada) agora é um wrapper fino que chama a implementação real (`runProductionLineInner`) dentro de um `try/catch` cobrindo a função inteira — qualquer exceção que escape de qualquer dependência (Postgres, descriptografia, bug futuro) cai num "falha genérica" que tenta rotear para `handleDeterministicFailure` (relendo a linha do banco) e, mesmo que essa releitura também falhe, ainda assim resolve normalmente. Isso é a garantia definitiva: `runProductionLine` **nunca** rejeita, então o BullMQ nunca mais vê esse job como `failed` por um bug de negócio — só o handler `"failed"` do worker como rede de segurança adicional (ex.: erro na própria infra do BullMQ/lock, fora do processor).
- **Teste de integração cobrindo exatamente o cenário relatado** (`apps/worker/src/production-line-worker.integration.test.ts`, mesmo Redis real efêmero do fix anterior): (a) um processor mockado que **rejeita de propósito** (simulando uma exceção real escapando) confirma que o job vai pra `failed` e, mesmo assim, o handler `"failed"` consegue recriar um job `delayed` novo — provando que `cancelLineRun` não fica mais bloqueado; (b) um teste separado sobe um `Worker` "cru" do BullMQ (sem os handlers de `production-line-worker.ts`) que sempre lança, deixando o job propositalmente preso em `failed`, e chama `syncActiveLines()` diretamente pra confirmar que ele detecta o estado morto, remove o job e recria — isolando a garantia de `syncActiveLines` da garantia do handler `"failed"`. `line-pipeline.test.ts` ganhou 2 testes novos forçando `getDecryptedApiKey` a rejeitar de verdade (não o caminho normal de "chave ausente") e confirmando que `runProductionLine` resolve normalmente mesmo quando a releitura de recuperação no catch também falha.
- **Recuperação imediata rodada contra produção**: com o fix aplicado localmente, chamei `syncActiveLines()` uma vez contra o Redis/Postgres reais de produção (script descartável, apagado depois de rodar) — como as 5 linhas já estavam saudáveis (ver primeiro parágrafo), a chamada não teve efeito (todas já tinham job `delayed` — comportamento correto e idempotente), mas confirma que o caminho de recuperação sob demanda funciona sem precisar reiniciar o worker.

## Bug real: reagendamento de linha ATIVA falhava silenciosamente por colisão de jobId no BullMQ (2026-08-27)

- **Causa raiz**: `scheduleLineRun(lineId, ...)` usa `jobId = lineId` (garante no máximo uma execução pendente por linha) e era chamado de dentro do próprio processor da linha — em `scheduleNext`, `handleDeterministicFailure`, `handleRateLimit` e no bloco de sucesso de `runProductionLine` — enquanto o job atual, com esse **mesmo** `jobId`, ainda estava `active` na fila. O BullMQ ignora silenciosamente qualquer `add()` com um `jobId` que já existe na fila em qualquer estado — active, waiting, delayed, completed ou failed (https://docs.bullmq.io/guide/jobs/job-ids) — sem lançar erro nem logar nada. Resultado: `nextRunAt` era persistido corretamente no Postgres (linha aparecia "Ativa" com hora certa na tela), mas nenhum job novo entrava de fato na fila; a linha só voltava a rodar se o worker reiniciasse (`syncActiveLines` re-detecta linhas órfãs no boot). A entrada anterior "PROMPT 3" deste arquivo descrevia esse desenho (reagendar "dentro do próprio processor, não em um listener 'completed'") como proposital, exatamente para "evitar condição de corrida" — na prática causava a corrida que tentava evitar; esta entrada substitui aquela descrição.
- **Por que os testes existentes não pegaram**: `line-pipeline.test.ts` mocka `scheduleLineRun` inteiro (`vi.mock("@wordbee/shared", ...)`), então nunca exercitava o comportamento real de colisão de `jobId` do BullMQ — só verificava que a função era chamada, não que a chamada realmente criava um job novo na fila.
- **Correção — mover todo o reagendamento para os handlers `worker.on("completed"/"failed")` do BullMQ** (`apps/worker/src/production-line-worker.ts`), em vez do processor: o BullMQ remove o job da fila (`removeOnComplete: true`/`removeOnFail`) **antes** de disparar esses eventos, então o `jobId = lineId` já está livre quando `scheduleLineRun` é chamado — sem colisão possível. `runProductionLine`/`handleDeterministicFailure`/`handleRateLimit` continuam persistindo `nextRunAt`/`status` no Postgres normalmente; só pararam de tocar na fila. `scheduleNext` foi inlined (não sobrou nenhuma outra utilidade além de gravar `nextRunAt`). O handler `"failed"` ganhou a mesma lógica de reagendamento como rede de segurança, mesmo `runProductionLine` sempre tratando erro internamente e "completando" hoje — cobre o caso raro de uma exceção não tratada escapar do processor.
- **Teste de regressão real do comportamento do BullMQ** (`apps/worker/src/production-line-worker.integration.test.ts`, novo arquivo): sobe um `redis-server` efêmero em processo filho (porta livre, sem persistência) em vez de mockar `scheduleLineRun` ou usar `ioredis-mock` — o BullMQ depende de scripts Lua e semântica de fila que mocks em memória não reproduzem com fidelidade suficiente para pegar essa classe de bug de verdade. Roda `startProductionLineWorker` real contra BullMQ+Redis reais (só a lógica de negócio e o Prisma são mockados), confirma que depois do job completar existe um job `delayed` com `jobId = lineId` na fila, e confirma que uma linha `PAUSADA` durante a execução não é reagendada. Pulado (`describe.skipIf`) se o binário `redis-server` não estiver disponível no ambiente. `line-pipeline.test.ts` ganhou `expect(scheduleLineRun).not.toHaveBeenCalled()` em todos os caminhos (sucesso, falha determinística, rate limit, idempotência) para travar que a função de negócio nunca mais toca na fila diretamente.

## Estado final da infraestrutura de produção — Railway descontinuada (2026-08-25)

- **Migração concluída e validada pelo usuário** com um teste real de ponta a ponta (linha de produção processada e artigo publicado de verdade pelo worker no EasyPanel). Este é o estado final de produção — as entradas anteriores ("Migração Railway -> VPS próprio (EasyPanel)", "Redis único via Upstash") registram a análise/plano que levou até aqui e continuam válidas como histórico, mas a arquitetura abaixo é a que está rodando de fato, e substitui qualquer menção a Railway como ambiente ativo no resto da documentação.
- **Arquitetura final — dois ambientes de deploy coordenados, dois serviços de dados compartilhados**:
  - **web** (Next.js) → **Vercel** (serverless). Produtor dos jobs BullMQ.
  - **worker** (BullMQ) → **EasyPanel**, um único serviço "App" (Docker) no VPS próprio. Consumidor dos jobs. Nenhum outro serviço roda no EasyPanel — sem Postgres nem Redis locais.
  - **Postgres** → **Neon** (gerenciado, externo), mesma instância para web e worker.
  - **Redis** → **Upstash** (gerenciado, externo), mesma instância para web e worker — fila BullMQ (produtor=web, consumidor=worker) e rate limit de login (só web).
- **Postgres também ficou fora do EasyPanel** (diferente do planejado na entrada "Migração Railway -> VPS" acima, que previa o template nativo de Postgres do EasyPanel): a implementação final usou **Neon** em vez disso, pela mesma razão já aplicada ao Redis — a Vercel roda serverless com **IP de saída dinâmico**, então um banco alcançável de forma confiável por ela precisa ter endpoint público pensado pra esse padrão (TLS, sem depender de allowlist de IP fixo). Neon já é assim nativamente. Efeito colateral positivo: o VPS/EasyPanel fica com **zero serviços com estado** — só o container do worker, que é stateless e descartável/recriável a qualquer momento sem risco de perda de dado. Backup, upgrade de versão e monitoramento de Postgres/Redis passam a ser 100% responsabilidade dos provedores gerenciados (Neon/Upstash), não mais algo a operar no próprio VPS.
- **Railway totalmente desligada**: nenhum serviço (web, worker, Postgres, Redis) roda mais lá. Toda menção a Railway como ambiente ativo foi removida de `README.md` e `VERCEL-ENV.md` (substituída por EasyPanel/Neon/Upstash); as entradas de `DECISIONS.md`/`PROGRESS.md` anteriores a esta data que mencionam Railway permanecem como registro histórico do que era verdade naquele momento (ex.: o bug de deploy do "web" na Railway, ou o plano inicial de migração) — não foram reescritas, só superadas por esta entrada.

## Redis único via Upstash — causa raiz de linhas de produção não processando pós-migração (2026-08-25)

- **Investigação de código, não bug de código**: confirmado (lendo `apps/web/src/lib/redis.ts`, `apps/web/src/lib/production-lines.ts`, `packages/shared/src/queue/index.ts`, `apps/worker/src/redis.ts`, `apps/worker/src/production-line-worker.ts`, `apps/worker/src/index.ts`) que **os três pontos de conexão Redis do sistema leem a mesma variável `process.env.REDIS_URL`**: (1) `packages/shared/src/queue/index.ts` — produtor, chamado pelo web via `scheduleLineRun`/`cancelLineRun` em `production-lines.ts` ao criar/pausar/retomar/excluir uma linha; (2) `apps/worker/src/redis.ts` (`createRedisConnection`) — consumidor, usado pelo `Worker` do BullMQ (`startProductionLineWorker`), pelo lock por linha e pelo heartbeat; (3) `apps/web/src/lib/redis.ts` (`getRedis`) — usado só pelo rate limit de login (`rate-limit.ts`). Não existe hoje nenhuma variável alternativa (`BULLMQ_REDIS_URL`, `UPSTASH_REDIS_REST_URL` etc.) sendo lida em lugar nenhum — busca completa por `REDIS`/`UPSTASH` no código confirma isso.
- **Causa raiz real do sintoma reportado ("worker não processa jobs")**: não é um bug de código — é configuração de ambiente. `REDIS_URL` da Vercel (web, produtor) e do worker (EasyPanel, consumidor) apontavam para Redis **diferentes** depois da migração (o worker foi apontado para o Redis interno do EasyPanel, inalcançável pela Vercel). Como a fila BullMQ só existe de fato dentro de um Redis específico, o worker nunca via os jobs que o web agendava — sem erro visível em nenhum dos dois lados (o job fica só esperando, "delayed", no Redis errado). Já era um risco antecipado (README.md, "Deploy no EasyPanel", primeira versão desta migração) mas documentado de forma insuficiente — a instrução dizia para reapontar a Vercel para a "connection string pública do Redis do EasyPanel", que dependia de expor esse Redis publicamente sem detalhar o problema de IP dinâmico da Vercel abaixo.
- **Decisão: manter uma única `REDIS_URL` para fila BullMQ + rate limit, não separar em duas variáveis.** Avaliado explicitamente (pedido do usuário) se seria mais robusto separar (`BULLMQ_REDIS_URL` vs. `RATE_LIMIT_REDIS_URL`, por exemplo), mesmo que as duas apontassem pro mesmo Upstash por ora. Descartado porque:
  - As duas cargas são leves (uso pessoal, um usuário, poucas tentativas de login e poucas linhas de produção) — não há cenário real de contenção ou necessidade de isolar performance entre os dois usos nesta escala.
  - Mais variáveis de ambiente para manter sincronizadas entre duas plataformas (Vercel + EasyPanel) é **mais** superfície para o exato tipo de erro que já causou este bug (divergência silenciosa entre ambientes), não menos — uma única `REDIS_URL` é mais fácil de auditar ("as duas plataformas têm o mesmo valor?") do que confirmar N variáveis em paralelo.
  - Já que ambas apontariam pro mesmo Upstash de qualquer forma, separar a variável não compra isolamento real nenhum hoje — só indireção. Se um dia houver motivo concreto para separar (ex.: mover rate limit para outro Redis por limite de conexões do plano gratuito do Upstash), é uma mudança pequena e isolada de fazer então, não algo que valha pagar o custo agora.
  - Risco aceito e documentado (pedido explícito do usuário): uma única `REDIS_URL` significa que um problema nesse Redis (queda, saturação de conexões) afeta simultaneamente login (rate limit) e Linhas de Produção (fila). Para uso pessoal de baixo volume, aceitável — anotado como trade-off consciente em comentários no código (`apps/web/src/lib/redis.ts`, `packages/shared/src/queue/index.ts`, `apps/worker/src/redis.ts`) e aqui, para não ser redescoberto como "confusão" numa investigação futura.
- **Redis deixa de ser template nativo do EasyPanel, passa a ser Upstash externo** (Postgres continua no EasyPanel — sem mudança nisso). Motivo: o produtor (web/Vercel) roda serverless com **IP de saída dinâmico** — não há como restringir com segurança o Redis do EasyPanel só para o(s) IP(s) da Vercel, e deixá-lo aberto para qualquer IP de origem é um risco desnecessário para expor um serviço com dados de fila/sessão. Upstash é desenhado justamente para esse padrão (endpoint público com TLS, otimizado para clientes serverless/edge) — mesma lógica já usada para o Postgres (também precisa ser publicamente alcançável pela Vercel), só que o Postgres do EasyPanel já suporta isso nativamente via "Networking" enquanto o Redis, por ser mais barato/simples de substituir por um serviço gerenciado dedicado, não compensa o mesmo caminho.
- **Comentários adicionados no código** (não só na doc) nos três pontos de leitura de `REDIS_URL`, deixando explícito que produtor e consumidor precisam apontar para o mesmo Redis e que a falha, se acontecer, é silenciosa — para que o próximo debug desse sintoma comece pela config, não pelo código.
- **Nenhuma variável de ambiente real foi alterada** (pedido explícito do usuário) — só código (comentários) e documentação (`README.md`, `.env.production.example`, este arquivo). A reconfiguração de fato do `REDIS_URL` na Vercel e no EasyPanel para o mesmo valor Upstash é manual, do usuário.

## Migração Railway -> VPS próprio (EasyPanel) — escopo e infra (2026-08-25)

- **Escopo confirmado com o usuário**: só **worker + Postgres + Redis** saem da Railway e vão para o VPS/EasyPanel. O app **web continua na Vercel** — não houve reversão da decisão registrada acima ("Deploy do 'web' na Railway — remoção do `output: standalone`"). `apps/web/Dockerfile` continua obsoleto/não usado; `next.config.mjs` não foi alterado. Cheguei a levantar a opção de mover tudo (web incluso) antes de mexer em qualquer arquivo, justamente porque o pedido original citava expor domínio+SSL pro serviço "web" no EasyPanel — o usuário optou pelo escopo menor.
- **`docker-compose.prod.yml` perdeu o serviço `web`** (mantém `worker`, `postgres`, `redis`, com healthcheck e `restart: unless-stopped` já existentes desde o PROMPT 4, confirmados de novo funcionando ponta a ponta: build, `up`, `migrate deploy`, worker conectando em Postgres/Redis e processando). Esse compose agora serve só para (a) validar localmente que a imagem do worker builda e roda antes de configurar o EasyPanel, e (b) um fallback documentado pra quem quiser um VPS "cru" via `docker compose` puro em vez do EasyPanel.
- **No EasyPanel: Postgres e Redis via templates nativos do EasyPanel, não via `docker-compose.prod.yml`.** Avaliadas as duas opções (import direto do compose com os três serviços vs. serviços individuais):
  - Templates nativos ganham em robustez de longo prazo pra uso pessoal: backup agendado com poucos cliques (S3/local) já embutido na UI do EasyPanel, upgrade de versão do Postgres/Redis assistido pelo painel, métricas de CPU/memória/disco por serviço prontas, e reinício/gestão de volume isolados do ciclo de vida do worker (atualizar a imagem do worker não deveria nunca arriscar o container de banco).
  - Um compose único importado como "serviço Compose" no EasyPanel gerencia os três containers como uma unidade menos granular na UI (backup/métricas por sub-serviço nesse modo são mais limitados) — pior para operação de longo prazo por uma única pessoa sem tooling de infra dedicado.
  - `worker` continua um `Dockerfile` próprio: sem alternativa de template pronto (é código da aplicação), deployado no EasyPanel como serviço "App" a partir do GitHub, apontando pra `apps/worker/Dockerfile` com contexto de build = raiz do repo.
- **`worker` não precisa de domínio/SSL/porta exposta no EasyPanel**: é um consumidor de fila BullMQ (`ioredis`), não sobe servidor HTTP — só precisa alcançar Postgres/Redis pela rede interna do EasyPanel (mesmo projeto) e ter as variáveis de ambiente configuradas. Isso simplifica o passo a passo do README: não há "expor porta" nem "configurar domínio" pra esse serviço, diferente do que o pedido original presumia (que viria da hipótese de mover o `web` junto).
- **`DATABASE_URL`/`REDIS_URL` da Vercel passam a apontar pro Postgres/Redis do EasyPanel** (endpoint público do serviço, já que a Vercel roda fora do VPS) — isso é uma reconfiguração manual no painel da Vercel, fora do escopo de arquivos deste repo; documentado no README como parte do passo a passo.
- **`ENCRYPTION_KEY` não é gerada de novo**: precisa ser copiada do valor atual (Vercel/Railway) pro novo ambiente, ou os dados já criptografados no banco (`api_keys.chave_encrypted`, `wp_sites.app_password_encrypted`) ficam ilegíveis. Documentado com destaque em `.env.production.example` e no passo a passo de migração de dados do README — o valor real nunca vai para o repo/código, só é copiado manualmente pelo usuário entre os dois painéis.
- **`scripts/backup.sh`/`scripts/restore.sh` reaproveitados para a migração** (em vez de escrever um script novo): ambos passaram a aceitar `DATABASE_URL` já exportada no ambiente como alternativa a ler do `.env` local, o que permite `DATABASE_URL="<url-railway>" ./scripts/backup.sh` seguido de `DATABASE_URL="<url-vps>" ./scripts/restore.sh <dump>` sem precisar editar nenhum arquivo — mesma ferramenta que já existe pra backup de rotina, sem duplicar lógica de `pg_dump`/`pg_restore` num script novo.

## Bug real de produção: crash "l.wpSite.nome" ao ativar/pausar linha + 400 no GET de reference-images (2026-08-25)

- **Causa raiz confirmada (hipótese do usuário estava certa)**: `pauseProductionLine`/`resumeProductionLine` (`apps/web/src/lib/production-lines.ts`) faziam `prisma.productionLine.update(...)` **sem** `include: { wpSite }`, enquanto a listagem (`/linhas-de-producao/page.tsx`) e o detalhe (`GET /api/production-lines/[id]`) sempre incluem `wpSite`. O tipo `ProductionLineSummary`/`ProductionLineDetail` declara `wpSite: { nome: string }` como **obrigatório**, mas o endpoint de toggle (`PATCH /api/production-lines/[id]`) devolvia uma linha sem essa chave — quebrando o contrato que o frontend assume, causando `TypeError` ao renderizar `{line.wpSite.nome}`.
- **Mesmo bug encontrado (e corrigido) em `createProductionLine`**, não só no toggle: o `.create()` também não tinha `include: { wpSite }`. Como `LinesClient.handleCreated` faz `setLines((prev) => [line, ...prev])` — um **prepend sem merge** — criar uma linha nova é, na prática, um caminho até mais direto pra esse crash do que o toggle (que tem `handleChanged` fazendo `{...l, ...updated}`, um merge que **acidentalmente** protege o `wpSite` antigo de sumir, já que `updated` não tem essa chave e o spread não apaga chaves ausentes na fonte). Ou seja: o toggle já estava parcialmente blindado por essa mecânica do merge; o `create` não tinha proteção nenhuma. Os dois foram corrigidos com o mesmo `include`, pra não depender dessa blindagem incidental do merge como única linha de defesa.
- **Correção**: as três funções de mutação de `ProductionLine` que devolvem a linha (`createProductionLine`, `pauseProductionLine`, `resumeProductionLine`) agora usam a mesma constante `WP_SITE_INCLUDE = { wpSite: { select: { nome: true } } }`, igual ao include já usado na listagem/detalhe — uma fonte única em vez de repetir o literal em 3 lugares e arriscar dessincronizar de novo.
- **Guard defensivo adicionado independente da causa raiz** (pedido explícito): `line.wpSite?.nome ?? "—"` em `LineCard.tsx` e `LineDetailClient.tsx`, com fallback "—" (mesma convenção já usada em `formatDateTime` pra valores ausentes). Um payload incompleto de qualquer endpoint futuro não deve mais quebrar a tela.
- **`GET /api/production-lines/[id]/reference-images` não existia** (só havia `POST`) — uma requisição GET pra essa URL cai no 405 padrão do App Router pra método não implementado. Nenhum código do frontend chama esse GET hoje (confirmado por busca no repo — `ReferenceImagesSection.tsx` só faz POST/DELETE), então a causa do "400" relatado não pôde ser localizada num call-site específico; o handler foi adicionado por ser o comportamento correto e faltante (paridade com o padrão REST já usado pelo resto da API) e por ser exatamente o que foi pedido: devolve `{ images: [] }` com 200 pra uma linha sem imagens, 404 se a linha não existir/não pertencer ao usuário, seguindo o mesmo padrão de autorização (`findFirst` por `id`+`userId`) já usado em `addReferenceImage`/`deleteReferenceImage`.
- **Validação manual (2026-08-25)**: rodada uma query direta contra o Postgres de produção reproduzindo exatamente a query corrigida (`findFirst` com o novo include) na linha real "teste" — confirmado `wpSite: { nome: "Renda Dinheiro" }` presente no resultado. A query equivalente ao novo GET de reference-images também testada contra essa linha real, confirmando `{ images: [] }` (linha sem imagens cadastradas). Não foi disparado o toggle de verdade pela UI/API (que chama `cancelLineRun`/`scheduleLineRun` via BullMQ e poderia acionar uma execução real de automação contra a linha "teste" sem necessidade) — a validação foi feita no nível da query/contrato de dados, que é onde o bug realmente estava.

## Bug real de produção: geração de artigo via OpenRouter travava para sempre (2026-08-25)

- **Causa raiz encontrada**: `fetchJsonOrThrow` (`packages/shared/src/ai/http.ts`), usado por **todos** os providers de texto/imagem (não só OpenRouter), chamava `fetchWithTimeout` — cujo `AbortController`/timer era cancelado (`finally { clearTimeout(timer) }`) assim que a promise de `fetch()` resolvia — e só **depois** disso lia o corpo da resposta (`res.text()`/`res.json()`). Como a promise de `fetch()` resolve assim que os *headers* chegam (não quando o corpo termina de chegar), a leitura do corpo ficava **sem nenhum timeout**. Para `generateTitles` (resposta pequena, termina rápido) isso nunca aparecia; para `generateArticle` via OpenRouter (resposta grande — um artigo HTML inteiro — e com a latência adicional do proxy do OpenRouter até o DeepSeek) o corpo podia demorar minutos pra terminar de chegar, e a chamada ficava pendurada indefinidamente, exatamente o sintoma relatado em produção (5+ min, sem erro, requisição "pending" no navegador).
- **Não era um bug específico do OpenRouter** — `generateTitles`/`generateArticle` já usavam (e continuam usando) o mesmo mecanismo de timeout (mesma função `chatCompletion` → `fetchJsonOrThrow`); o bug estava no utilitário compartilhado, só que o formato de resposta e a latência do OpenRouter o tornavam visível primeiro ali. Todos os outros providers (OpenAI, Gemini, Grok) tinham a mesma exposição latente para `generateArticle`/`generateImage`, só não haviam sido notados ainda.
- **Correção em `http.ts`**: `fetchJsonOrThrow` agora envolve `fetch()` **e** a leitura do corpo da resposta num único `AbortController`/timer (helper interno `withTimeout`), então um corpo lento também aciona o abort e vira `AiErrorCode "timeout"` — não fica mais pendurado. `fetchWithTimeout` (usado só por `validateXKey` e download de imagem já pronta, que não leem corpo grande) manteve seu contrato original (cobre só o `fetch()`), documentado explicitamente no código para não repetir o erro.
- **`DEFAULT_TIMEOUT_MS` subiu de 30s para 60s**: como o timeout agora realmente é aplicado à leitura do corpo inteiro (antes, na prática, não era — daí o bug), manter 30s teria criado uma regressão nova: `generateArticle`/`generateImage` de OpenAI/Gemini/Grok (que hoje "funcionam" só porque o timeout nunca os alcançava de verdade) passariam a estourar timeout de verdade em 30s, tempo insuficiente pra geração de conteúdo real. 60s é um piso mais seguro para qualquer chamada que não especifique um timeout próprio.
- **`ARTICLE_TIMEOUT_MS = 90_000` explícito só no OpenRouter** (`packages/shared/src/ai/openrouter.ts`), passado à mesma `chatCompletion`/`fetchJsonOrThrow` usada por `generateTitles` — mesmo mecanismo, janela maior porque é o provider onde o problema foi confirmado em produção e cuja latência (proxy até o DeepSeek) é a mais alta observada. `generateTitles` continua no padrão (60s) — não faria sentido título esperar 90s por uma resposta que deveria ser rápida.
- **`maxDuration = 300` da rota `POST /api/articles/generate`** (`apps/web/src/app/api/articles/generate/route.ts`) já era maior que qualquer timeout de provider (60-90s) — confirmado e documentado com um comentário no próprio arquivo; nenhuma mudança necessária ali. Esse `maxDuration` só tem efeito real em Functions da Vercel; na Railway (`next start` como processo Node comum) o limite relevante é o `requestTimeout` default do Node (5 min), também confortável.
- **Teste de regressão simula o cenário exato do bug**: mock do `fetch()` que resolve na hora (headers OK) mas cujo `.json()` só resolve/rejeita quando o `AbortSignal` passado a ele dispara — reproduz fielmente o comportamento real do undici ao abortar a leitura do corpo. Rodado com `vi.useFakeTimers()`/`vi.advanceTimersByTimeAsync()` para não precisar esperar 90s de verdade no test runner. Esse teste falharia (ficaria pendurado) contra o código antigo.

## Remoção de chave de API pela UI (2026-08-25)

- **Hard delete, não soft-delete**: `deleteApiKey` (`apps/web/src/lib/api-keys.ts`) apaga a linha da tabela `api_keys` de vez (`prisma.apiKey.deleteMany`), em vez de marcar um campo tipo `ativa: false`. Motivo: (1) nada no app precisa de histórico/auditoria de chaves removidas (diferente de `Article`, cujo histórico é requisito explícito do PRD); (2) a constraint única `@@unique([userId, provider, tipo])` já existe e o fluxo de recadastro usa `upsert` — soft-delete exigiria excluir linhas "removidas" dessa constraint e de toda leitura (`listApiKeyCards`, `getDecryptedApiKey`, `listConfiguredProviders`) para não bloquear/confundir um recadastro, complexidade sem benefício real num app pessoal de usuário único.
- **`deleteMany` em vez de `delete`, de propósito**: `delete` lançaria `RecordNotFoundError` se a chave já não existisse; `deleteMany` apaga zero linhas silenciosamente. Isso torna a operação idempotente (RF implícito: clicar "Remover" duas vezes, ou a chave já ter sido removida em outra aba, nunca deveria virar erro 500) sem precisar de um `findFirst` prévio.
- **Chave compartilhada (OpenAI/Gemini/OpenRouter) reflete nos dois cards automaticamente, sem código extra**: como `tipoForSave` já mapeia esses provedores para uma única linha `tipo=AMBOS`, e `listApiKeyCards` já lê essa mesma linha para os dois cards (texto e imagem) via `tiposToQuery`, apagar essa linha uma vez já é suficiente — não existe uma "remoção em cascata" para implementar, é a mesma leitura que já existia refletindo o novo estado.
- **Rota `DELETE /api/api-keys/[provider]/[capability]`** (dynamic route params, não query string): segue o mesmo padrão já usado em `/api/wp-sites/[id]` e `/api/production-lines/[id]/titles/[titleId]`, em vez de introduzir um estilo novo de rota com query string só para esse endpoint.
- **Sem endpoint dedicado de "remoção em lote"**: cada card dispara sua própria chamada DELETE; como a operação já é idempotente e barata, não há necessidade de um endpoint que remova várias chaves de uma vez.

## OpenRouter como provedor de imagem (2026-08-25)

- **Motivo de negócio**: evitar depender só da cota diária gratuita do Gemini direto (1500 req/dia texto, **500/dia imagem**, já esgotada em testes anteriores — ver PROMPT 2/3) e consolidar o billing pago em um único provedor (OpenRouter), já integrado para texto nesta mesma entrega.
- **Endpoint próprio, diferente do de texto**: o OpenRouter tem uma Image API dedicada (`POST /images`, formato de request/response distinto de `/chat/completions`) — `createOpenRouterImageProvider` (`packages/shared/src/ai/openrouter.ts`) implementa `ImageProvider` chamando esse endpoint, reaproveitando a mesma constante `EXTRA_HEADERS`/autenticação Bearer do provider de texto no mesmo arquivo.
- **Modelo padrão confirmado na fonte (2026-08-25)**: `google/gemini-2.5-flash-image` ("Nano Banana") via `GET /api/v1/models?output_modalities=image` — mesmo modelo comercial já usado no provider Gemini direto, agora acessível também via OpenRouter. Configurável por `OPENROUTER_IMAGE_DEFAULT_MODEL`.
- **Imagens de referência via `input_references`** (array de `{ type: "image_url", image_url: { url } }`, aceitando `data:` URL): o array de `referenceImages` (já limitado a 5 por linha em `production-lines.ts`, RF-25) é repassado integralmente como `data:${mimeType};base64,${base64}` — nenhum limite adicional no provider, mesmo padrão do `gemini.ts` (que também apenas itera o array recebido).
- **Fallback silencioso quando o modelo não suporta `input_references`**: a API não tem um jeito barato de checar `supported_parameters` do endpoint antes de cada chamada (exigiria uma requisição extra à Image Models API a cada geração), então o cliente tenta com referência e, se o OpenRouter responder 400 mencionando `input_references` no corpo, refaz a chamada sem referência (loga um aviso, não falha o artigo). Um 400 por outro motivo (ex.: prompt ausente) continua propagando o erro normalmente — só esse padrão específico aciona o fallback.
- **Reaproveita o `AiErrorCode` "insufficient_credits"** já criado para o provider de texto (mesmo status 402, mesma API/conta de billing do OpenRouter).
- **Chave compartilhada entre texto e imagem (RF-13)**: `tipoForSave` (`apps/web/src/lib/api-keys.ts`) passou a tratar `OPENROUTER` como `AMBOS`, igual a OpenAI/Gemini — o card na aba "IAs para Imagens" reaproveita a mesma chave já validada na aba de texto, sem pedir de novo (mesmo mecanismo de `listApiKeyCards`/`ProviderCard`, nenhuma tela nova).
- **Sem select hardcoded para ajustar**: adicionar a entrada em `IMAGE_PROVIDERS` (`packages/shared/src/ai/registry.ts`, com `suportaImagensReferencia: true`) foi suficiente para o OpenRouter aparecer nos selects de "IA para imagem" de Criar Artigo e Nova Linha de Produção — ambos já liam a lista de provedores configurados dinamicamente (confirmado na entrega do provider de texto).

O OpenRouter aceita outros métodos de pagamento e permite recargas pequenas, servindo o mesmo modelo (DeepSeek V4 Flash) via uma API compatível com o formato da OpenAI.

## Deploy do "web" na Railway — remoção do `output: "standalone"` (2026-08-25)

- **Bug real em produção**: o serviço "web" na Railway (build via Railpack, sem Dockerfile customizado) falhava logo após o start com `"next start" does not work with "output: standalone" configuration` e o processo caía por `SIGTERM` em loop. Causa: `next.config.mjs` desativava `standalone` só quando `process.env.VERCEL` estava definido (ver decisão anterior), mas a Railway não define essa variável — então o build gerava `.next/standalone`, e o script `"start": "next start"` do `apps/web/package.json` (inalterado, é o padrão do create-next-app) é incompatível com esse modo, que exigiria `node .next/standalone/server.js`.
- **Corrigido removendo `output: "standalone"` por completo** do `next.config.mjs`, em vez de estender a condicional para também detectar a Railway (ex.: `RAILWAY_ENVIRONMENT_NAME`). Motivo: nem Vercel nem Railway (os dois destinos reais do "web" hoje) fazem build a partir de `apps/web/Dockerfile` ou leem `.next/standalone` — ambos usam Railpack/empacotamento nativo próprio. Manter `standalone` como caso especial só complicava o `package.json` (exigiria trocar `start` condicionalmente por plataforma) sem nenhum benefício.
- **Efeito colateral aceito conscientemente**: `apps/web/Dockerfile` (usado pelo caminho alternativo "VPS único" via `docker-compose.prod.yml`, descrito no `README.md` e validado no PROMPT 4) depende de `.next/standalone` e **para de funcionar** para o `web` a partir desta mudança — decisão confirmada com o usuário, que optou por abandonar esse caminho para o `web` em favor de Vercel/Railway. O Dockerfile foi marcado como obsoleto (comentário no próprio arquivo) em vez de removido, para não destruir histórico/documentação sem necessidade. O `apps/worker/Dockerfile` **não** é afetado — é um build separado, multi-stage com `node` puro, que nunca dependeu do output do Next.js.

## Deploy na Vercel — correção do build do monorepo

- **Bug real encontrado no primeiro deploy na Vercel**: `Module not found: Can't resolve '@wordbee/db'`. Causa: a Vercel roda o build com "Root Directory" = `apps/web` (suporte nativo dela a monorepos — instala a partir da raiz do workspace, mas builda a partir do subdiretório), então `npm run build` executava só o script do `apps/web/package.json` (`next build`), pulando o script raiz `build:libs` que compila `packages/shared` e `packages/db` para `dist/` antes. Localmente isso nunca apareceu porque sempre rodamos o build a partir da raiz do monorepo.
  - **Corrigido tornando `apps/web/package.json`'s `build` autossuficiente**: `"build": "cd ../.. && npm run build:libs && cd apps/web && dotenv -e ../../.env -- next build"` — funciona não importa de onde a plataforma de deploy invoque `npm run build` (raiz ou `apps/web`), sem depender de configurar corretamente o "Root Directory"/"Build Command" no painel da Vercel. Testado localmente simulando exatamente o comportamento da Vercel (build direto de dentro de `apps/web`, sem `dist/` pré-existente).
- **`output: "standalone"` desativado automaticamente na Vercel** (`process.env.VERCEL ? undefined : "standalone"`): esse modo é só para o deploy via Docker/VPS, onde `apps/web/Dockerfile` espera `.next/standalone`. A Vercel usa seu próprio empacotamento serverless e não precisa (nem deveria receber) esse output — a Vercel define `VERCEL=1` automaticamente em todo build, então a mesma base de código serve os dois destinos sem arquivo de config separado.

## PROMPT 4 — Fidelidade visual, robustez e deploy

- **SSRF completo com resolução de DNS** (`assertSafeWordPressUrl` em `packages/shared/src/wordpress/url-guard.ts`): além do bloqueio de IP/hostname literal (PROMPT 2), agora resolve o hostname via `dns.promises.lookup` e bloqueia se qualquer endereço resolvido cair em faixa privada — impede que um domínio público aponte (ou seja re-apontado depois, DNS rebinding) para a rede interna. Não elimina 100% o TOCTOU entre a checagem e a conexão (exigiria fixar o IP resolvido no socket do fetch), mas cobre o caso prático relevante para um app pessoal. 5 novos testes.
- **Indicador de saúde do worker via heartbeat no Redis** (`packages/shared/src/worker-health.ts`), não uma tabela no Postgres: o worker grava `worker:heartbeat` a cada 30s com TTL de 90s (a chave expira sozinha se o worker cair, sem precisar de lógica extra de "está vivo?") e `worker:last_success` a cada publicação bem-sucedida. O Dashboard lê os dois via o mesmo Redis já usado para rate limit de login.
- **Logs do worker em JSON estruturado** (linha, evento, detalhe, duração do "tick") em vez de texto livre — mais fácil de agregar/filtrar em produção (`docker compose logs worker | jq`).
- **Toasts adicionados nos fluxos que só tinham feedback inline** (Chaves de API, cadastro/edição de site, criação de linha, resultado do gerador de artigo) para atender "toasts para toda ação de sucesso/erro" — mantendo também o feedback inline onde ele já fazia sentido (erros de validação de formulário).
- **`loading.tsx`/`error.tsx` no nível do grupo `(dashboard)`**, não por página: como todas as páginas do painel compartilham o mesmo layout e a mesma necessidade de skeleton/estado de erro, um par de arquivos no grupo já cobre a árvore inteira (convenção do App Router) sem duplicar 7 vezes.
- **Backup/restore via `pg_dump`/`pg_restore` em scripts shell simples** (`scripts/backup.sh`/`restore.sh`) em vez de uma ferramenta dedicada — suficiente para um Postgres único de uso pessoal, sem dependência nova. `restore.sh` exige confirmação digitada (`restaurar`) por ser destrutivo.
- **Dockerfiles multi-stage buildados e testados de verdade** (não só escritos): usei `colima` para ter um daemon Docker neste ambiente, buildei as duas imagens, subi a stack completa via `docker-compose.prod.yml` (Postgres+Redis+web+worker), rodei migração e seed exatamente como documentado no README, e confirmei login funcionando através do container na porta 3000. A imagem do worker copia `node_modules` completo (não passa pelo tracing do Next), já que ele roda via `node` puro e precisa do `prisma` CLI disponível para `migrate deploy`/seed em produção.
- **Sem CSRF token dedicado**: os cookies de sessão usam `SameSite=Lax` (já configurado no PROMPT 1), que por padrão do navegador não é enviado em requisições cross-site que não sejam navegação de topo — cobre o cenário relevante de CSRF para as rotas de mutação da API sem precisar de um token extra, aceitável para um app single-user sem endpoints de mutação públicos além do login.

## PROMPT 3 — Linhas de Produção, worker, fila de títulos e histórico

- **Agendamento via job BullMQ auto-reagendado (jobId = lineId) em vez de repeatable jobs nativos do BullMQ.** Repeatable jobs do BullMQ são difíceis de reconfigurar dinamicamente (pausar/retomar/mudar intervalo por linha). Em vez disso, cada execução ("tick") agenda explicitamente a próxima via `scheduleLineRun(lineId, delayMs)` — com `jobId=lineId` garantindo no máximo uma execução pendente por linha. O reagendamento acontece só depois que o job atual termina (dentro do próprio processor, não em um listener "completed"), evitando qualquer condição de corrida no reuso do jobId.
- **"Um tick da linha nunca lança para o BullMQ."** `runProductionLine` captura e trata todo erro internamente (grava `Article` como FALHA, atualiza contadores, reagenda) e sempre retorna normalmente. Toda a lógica de retry (3 tentativas com backoff) e as regras de negócio (máximo atingido, rate limit, 5 falhas consecutivas) vivem dentro dessa função — o BullMQ nunca precisa saber de nenhuma dessas regras nem fazer retry de job.
- **Lock por linha via Redis `SET NX PX`** (chave `line-lock:{lineId}`, TTL de 10 min), adquirido pelo processor do BullMQ antes de chamar `runProductionLine` e liberado no `finally`. Garante que, mesmo que dois processos worker rodem por engano ao mesmo tempo (ex.: deploy com múltiplas réplicas sem querer), a mesma linha nunca é processada em paralelo.
- **Concorrência por provedor de IA via semáforo Redis (`INCR`/`DECR` com poll curto)**, não um limitador nativo do BullMQ (que limitaria por fila inteira, não por provedor). `AI_PROVIDER_CONCURRENCY` (padrão 3) limita quantas chamadas simultâneas por provedor rodam entre todas as linhas ativas.
- **Idempotência via `idempotencyKey` determinística**: `line:{lineId}:title:{titleQueueItemId}` quando o título vem da fila, ou `line:{lineId}:adhoc:{timestamp}` quando é gerado na hora. Antes de processar, o worker verifica se já existe um `Article` não-FALHA com essa chave e, se existir, pula (idempotência real contra reprocessamento).
- **Retry parcial e inteligente**: cada nova tentativa dentro do loop de 3 releem o `Article` do banco e só regeram o que ainda falta (conteúdo/imagem já persistidos numa tentativa anterior não são regerados). Isso exigiu adicionar `wp_media_id`, `ia_texto`, `ia_imagem`, `categoria_wp_id`, `wp_status_alvo`, `tema` e `prompt_customizado` ao modelo `Article` (4 migrações pequenas) — sem esses campos não seria possível reenviar ou retomar um artigo sem regerar tudo à toa, requisito explícito do PRD.
- **Rate limit vs. sobrecarga temporária tratados igual no nível da linha**: tanto `rate_limit` (429, cota do usuário) quanto `unavailable` (502/503/504, sobrecarga do provedor) dão positive para "adiar ou pausar" a linha (`rateLimitBehavior`), já que do ponto de vista da automação a ação certa é a mesma. Timeout (nosso próprio limite de 30s) continua contando como falha determinística normal, pois não necessariamente indica problema do lado do provedor.
- **Reposição da fila de títulos**: depois de cada publicação bem-sucedida, o worker gera 1 novo título só se a fila tiver menos de 3 pendentes — evita gerar títulos demais sem necessidade e mantém sempre alguns prontos.
- **"Atualizar" na página de detalhe da linha busca dados via API**, não `router.refresh()` puro, porque a página tem estado local (fila de títulos, galeria de imagens) que precisa ser resincronizado explicitamente após ações do usuário.
- **Histórico com filtros via query string da URL** (Server Component lendo `searchParams`), não uma API de listagem separada — padrão idiomático do App Router, dá paginação/filtro compartilháveis por link de graça.
- **Storage local exige caminho absoluto em `STORAGE_LOCAL_PATH`.** Como `apps/web` e `apps/worker` rodam com `cwd` diferentes (cada um na sua pasta), um caminho relativo resolveria para diretórios diferentes em cada processo — o worker precisa ler as mesmas imagens de referência que o web salvou.
- **`bullmq` adicionado a `serverComponentsExternalPackages` no `next.config.mjs`** (junto com `@node-rs/argon2`): evita que o webpack tente resolver o adaptador opcional `@valkey/valkey-glide` do bullmq (não instalado, não usado — só suportamos Redis puro via `ioredis`).
- **Validação real ponta a ponta do worker (2026-08-24)**: criei uma linha de produção de verdade usando a chave Gemini e o site `rendadinheiro.com.br` já configurados no PROMPT 2. O worker gerou um título real, gerou conteúdo HTML real, e corretamente classificou/tratou tanto um timeout quanto um 429 (mesma cota de imagem gratuita já esgotada do PROMPT 2) — a linha foi reagendada corretamente em ambos os casos, sem travar nem duplicar. Isso revelou e corrigiu dois bugs reais: (1) `handleDeterministicFailure` gravava `nextRunAt` como "agora" no banco enquanto o job real era agendado para `intervaloMin` no futuro — painel mostraria hora errada; (2) faltava log de observabilidade quando o rate limit acontecia durante geração de conteúdo/imagem (só existia para o título). Publicação de fato (upload de mídia + criação do post) segue não validada por falta de cota de imagem disponível — mecanismo já coberto por testes unitários do cliente WordPress (PROMPT 2).

## PROMPT 2 — Chaves de API, Sites WordPress e geração unitária

- **Bug crítico encontrado e corrigido: `fetch` global do Next.js quebra chamadas HTTP server-to-server.** O Next.js substitui `globalThis.fetch` do processo por uma versão própria (camada de cache/instrumentação de dados). Nos testes manuais, essa versão fazia com que respostas de erro HTTP normais (ex.: 401 da OpenAI, 400 da Gemini) virassem exceções genéricas em vez de um `Response` inspecionável, quebrando toda a classificação de erros (RF-15/RF-23). Corrigido importando `fetch` explicitamente do pacote `undici` em vez de usar o global, tanto no cliente de IA (`packages/shared/src/ai/http.ts`) quanto no cliente WordPress (`packages/shared/src/wordpress/client.ts`). Coberto por testes que mockam o módulo `undici` diretamente.
- **Gemini retorna HTTP 400 (não 401) para chave de API inválida.** `classifyHttpError` foi estendido para reconhecer o padrão "API key not valid"/`API_KEY_INVALID` no corpo de respostas 400 e tratá-las como `invalid_key`, além dos códigos 401/403 usados pelos outros provedores.
- **Modelos e endpoints de IA (pesquisados na documentação oficial de cada provedor em 2026-08-24, ver `packages/shared/src/ai/models.ts`):**
  - OpenAI: `POST /v1/chat/completions` (texto, `gpt-4o`) e `POST /v1/images/generations` (imagem, `dall-e-3`), padrão bem estabelecido.
  - Gemini: `POST /v1beta/models/{model}:generateContent` com header `x-goog-api-key`; imagem via `gemini-2.5-flash-image` ("Nano Banana") com `generationConfig.responseModalities: ["TEXT","IMAGE"]` e imagens de referência como `inlineData` nas `parts` do request. **Validado com chave real**: o modelo de texto `gemini-2.5-flash` citado pelo PRD já não existe mais para novas chaves (a própria API retorna 404 recomendando `gemini-3.6-flash`) — o padrão de `GEMINI_TEXT_MODEL` foi atualizado para `gemini-3.6-flash`. O modelo de imagem `gemini-2.5-flash-image` continua válido.
  - xAI/Grok: endpoint de texto compatível com a API da OpenAI (`POST https://api.x.ai/v1/chat/completions`); endpoint de imagem separado (`POST https://api.x.ai/v1/images/generations`). O rótulo comercial "Grok Imagine" (usado na UI, conforme o PRD) mapeia para o model id atual `grok-2-image` na API — configurável via `GROK_IMAGE_MODEL`, documentado por já ter havido troca de nomenclatura no passado.
  - Stability AI: `POST /v2beta/stable-image/generate/sd3` (multipart/form-data), modelo `sd3.5-large`, `Accept: application/json` para receber a imagem em base64 direto na resposta.
- **`metaTitle` retornado pela IA é reaproveitado como título final do post** (quando ≤ 60 caracteres), em vez de descartado. Como o WordPress puro não tem campo nativo de "meta title" sem um plugin de SEO (Yoast/RankMath — fora de escopo do MVP), usar esse título refinado como o próprio `title` do post é a forma mais direta de cumprir o requisito de "SEO básico (meta title ≤ 60 chars)" do PRD sem integrar um plugin.
- **Chave de API só é salva se a validação no provedor for bem-sucedida** (RF-15). Uma chave inválida nunca é persistida — o usuário recebe o erro e pode tentar de novo. Evita que uma chave quebrada fique "configurada" silenciosamente.
- **Progresso em tempo real do gerador unitário via streaming NDJSON** (newline-delimited JSON) em vez de Server-Sent Events. Motivo: o formulário envia a requisição via `POST` com corpo JSON — `EventSource` nativo só suporta `GET`. Um `ReadableStream` simples lido via `fetch().body.getReader()` no cliente evita a complexidade de SSE sem perder o requisito de "progresso visível (título → conteúdo → imagem → publicando)".
- **Guarda anti-SSRF básica (bloqueio de hostname/IP literal privado)** já implementada em `packages/shared/src/wordpress/url-guard.ts` e coberta por testes. A blindagem completa contra DNS rebinding (resolução de DNS antes de conectar) é a varredura de segurança explícita do PROMPT 4 — aqui cobre o caso comum (localhost, 127.0.0.1, RFC 1918) sem bloquear o fluxo de cadastro de site.
- **Tipos client-safe duplicados fora de `@wordbee/shared`** (`apps/web/src/lib/article-type-options.ts`, `criar-artigo-types.ts`, `wp-sites-types.ts`) em vez de importar tipos do barrel `@wordbee/shared` em componentes cliente. O barrel único do pacote (`export * from` em cada módulo) reexporta também os módulos que usam `node:crypto`/`undici`; embora seja teoricamente tree-shakeable, duplicar as poucas constantes/tipos realmente usados no cliente é mais seguro e barato do que arriscar node-builtins vazando para o bundle do browser.
- **Reenvio de imagem de referência (Gemini) não implementado ainda** — RF-21 do gerador unitário não inclui upload de imagens de referência (isso é exclusivo das Linhas de Produção, RF-25, escopo do PROMPT 3). A interface `ImageProvider.generateImage` já aceita `referenceImages` opcional para não precisar mudar a assinatura depois.
- **Novo `AiErrorCode` "unavailable"** adicionado para respostas 502/503/504 (modelo temporariamente sobrecarregado), distinto de `rate_limit` (429, cota do usuário). Descoberto na validação real abaixo — a Gemini retornou 503 "high demand" em `gemini-3.6-flash" durante o teste, e antes disso caía no genérico `unknown`.
- **Validação ponta a ponta com credenciais reais do usuário (2026-08-24)**: chave Gemini real + site WordPress real (`rendadinheiro.com.br`). Resultado: chave validada e salva (compartilhada entre texto/imagem), conexão com o site confirmada como administrador, categorias reais carregadas, título e conteúdo gerados de verdade pela Gemini e o artigo de teste foi salvo como **rascunho** (não publicado) por segurança — quando a etapa de imagem falhou com 429 (cota de geração de imagem da conta Gemini gratuita esgotada, não um bug), o `Article` ficou corretamente com `status=FALHA` e a mensagem de erro certa, visível no Dashboard/Histórico. Prova que o pipeline, a UI de progresso e o tratamento de erro funcionam ponta a ponta contra APIs reais; só não foi possível validar `uploadMedia`/`createPost` de fato por causa da cota de imagem da chave de teste.

## PROMPT 1 — Fundação

- **Gerenciador de pacotes: npm workspaces.** Já disponível no ambiente, zero instalação extra, suporte nativo a monorepo suficiente para o escopo do projeto.
- **ORM: Prisma** (o PRD permitia Prisma ou Drizzle). Prisma tem migrations maduras e o schema da seção 5 do PRD mapeia diretamente para `schema.prisma`.
- **Prisma na major 5 (5.22.x), não a 7.x mais recente.** Evita churn de duas majors no meio da construção; 5.x é estável e bem documentada. Revisitar upgrade pós-MVP.
- **Hash de senha: Argon2** via `@node-rs/argon2` (binário nativo pré-compilado, sem node-gyp). PRD permitia argon2 ou bcrypt; argon2 é a recomendação atual da OWASP.
- **Sessão: JWT assinado (HS256, `jose`) + registro em `sessions` no Postgres**, não NextAuth (proibido pelo PRD) e não JWT puro sem estado. Precisamos revogar sessões individualmente (RF-02 "sessões ativas"), o que um JWT stateless sozinho não permite.
- **Auth em duas camadas.** O middleware (Edge runtime no Next 14, sem acesso a Postgres) faz apenas a checagem rápida de assinatura/expiração do JWT. A checagem autoritativa (sessão revogada?) acontece em `getCurrentSession()` (Node.js runtime), chamada pelo layout do painel e por cada rota de API. Necessário porque o Next 14 não roda middleware em runtime Node.js.
- **Componentes de UI acessíveis via Radix UI** (Dialog, Tabs, Toast, Switch) em vez de implementar do zero. O PRD exige navegação por teclado, ESC para fechar modais e trap de foco — Radix entrega isso pronto e testado.
- **Tema claro/escuro: `next-themes` (localStorage) como fonte da verdade para a UI**, com sincronização best-effort para a coluna `users.tema_ui` a cada troca (fire-and-forget). Evita complexidade de flash-of-wrong-theme no SSR mantendo o campo do schema útil/persistido.
- **Compartilhamento de chave de API (RF-13):** constraint única em `(userId, provider, tipo)`. OpenAI e Gemini salvam com `tipo=AMBOS` (uma linha só, usada nas duas abas). Grok e Stability mantêm linhas separadas por tipo, já que o PRD só cita OpenAI/Gemini como provedores de chave compartilhada.
- **Next.js fixado em `^14.2.35`** (última patch da série 14.2), não Next 15/16. Elimina a maior parte dos CVEs conhecidos sem forçar uma migração disruptiva do App Router no meio da construção. Os achados residuais do `npm audit` (principalmente avisos ligados a Server Actions/RSC cache que não usamos e a um CVE moderado do esbuild que só afeta o dev server) foram aceitos como risco baixo para um app pessoal, single-user, sem CDN na frente, atrás de login — revisitar upgrade para Next 15+ como melhoria futura.
- **`export const dynamic = "force-dynamic"` no layout raiz.** O app inteiro é pessoal e autenticado (saudação por usuário, sessão via cookie) — nada deveria ser pré-renderizado estaticamente. Isso também contorna um bug conhecido do Next.js 14 (`Error: <Html> should not be imported outside of pages/_document` ao gerar `/404`/`/500` estaticamente); ver nota abaixo.
- **Regra dura: nunca definir `NODE_ENV` no `.env`.** Causou o bug acima quando o `dotenv-cli` injetava `NODE_ENV=development` durante `next build` (que precisa rodar como produção). O `next dev`/`build`/`start` e o worker já definem o valor certo sozinhos; documentado em `.env.example`.
- **Resolução dos pacotes internos (`@wordbee/shared`, `@wordbee/db`):** `package.json` expõe tanto `dist/` compilado (usado por produção e por typecheck) quanto o TypeScript fonte via export condition `"development"` (usado por `tsx`/Next em dev). Como nem toda ferramenta ativa essa condition de forma confiável, os scripts `dev`/`dev:worker`/`typecheck`/`build` sempre rodam `build:libs` primeiro para garantir que `dist/` exista.
- **Redis reaproveitado** para BullMQ (worker) e para rate limiting de login (web) — uma única peça de infra a mais, em vez de outra store separada.
- **Dashboard do Prompt 1 é esqueleto estático** (métricas zeradas, sem consulta ao banco). Dados reais são escopo explícito do PROMPT 2 ("DASHBOARD REAL") no documento de prompts.
- **Sem pasta `/referencia` com screenshots do Wordbee** no projeto (mencionada como opcional nas Observações do documento de prompts). A fidelidade visual seguiu a descrição textual do PROMPT 0 (sidebar roxo/grafite, cards brancos raio ~12px, gradiente roxo→magenta, etc.).
